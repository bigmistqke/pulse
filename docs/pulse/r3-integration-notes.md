# r3 integration notes — how the scope overlay meets the engine

Study for [Plan 2](../superpowers/plans/2026-07-08-speculation-engine-02-r3-integration-study.md): what r3 (`node_modules/r3/src/index.ts`) actually does, and what that forces on the integration of Plan 1's pure scope/slot/chain-match overlay ([`scope.ts`](../../src/scope.ts)). Findings first; the architecture decision it drives is [ADR 0010](../adr/0010-speculation-overlay-above-r3.md).

## r3 in one paragraph

r3 is an alien-signals-derived push-pull engine. A `Signal` is `{ subs, subsTail, value }` — **exactly one `value` per node**. A `Computed` adds `deps`, `flags` (`Check`/`Dirty`/`RecomputingDeps`/`InHeap`), `height`, dirty-heap pointers, `disposal`, `fn`, and `child`. Edges are alien-signals `Link`s (doubly linked on both dep and sub sides). Writes push (`setSignal` → `insertIntoHeap(sub)` for each sub); reads pull (`read` → `link(el, context)` + `updateIfNecessary`). Scheduling is a **height-ordered dirty heap** drained by `stabilize()` low-height-first, so propagation is glitch-free. `child`/firewall signals are signals *owned by* a computed.

The load-bearing fact: **one value per node.** Per-scope slots cannot live in r3's `value` — which is why Plan 1 stores them on the scope (`scope.slots`), separate from r3. Plan 1 is therefore already an overlay; these notes work out how that overlay drives invalidation and bridges to r3 at commit.

## Probe answers

**1. Speculative compute path — feasible, on a pulse-side path.** r3's `recompute(el)` (index.ts:154) sets `context = el`, runs `el.fn()`, and writes the result into `el.value` — the *committed* cell. To hold a derived's value at scope `S` without clobbering `el.value`, pulse must run the node's recipe under `S` on its own path: read walk hits a computed under `S`, finds no `S`-slot, runs the recipe (`defaultRecipe`, per Q7) with the ambient scope set to `S`, its inner reads form **pulse edges** (`linkEdge`, targetScope `S`) and populate an `S`-slot, and the result caches in `scope.slots[node]`. This *bypasses* r3's `recompute`/`el.value` entirely for the speculative case. It reuses none of r3's compute machinery — it reimplements the "run recipe, track deps" loop with pulse edges instead of r3 `Link`s. Cost: a parallel compute path for speculative reads. (Consistent with the `doubleName` trace, which populates `doubleName.slots[S]` by running the recipe under `S`.)

**2. Two edge systems — coexist, because they are temporally disjoint.** Committed reactivity uses r3 `Link`s (fired via the heap); speculation uses pulse `Edge`s (`scope.edges`, chain-match), which `closeScopeEdges` (scope.ts) tears down at close. There is no double-fire *provided commit order is: tear down the scope's pulse edges first, then promote*. On commit: `closeScopeEdges(S)` unlinks S's pulse edges and drops S's slots; *then* promotion calls `setSignal(node, committedValue)` for each writeSet node, which fires the committed consumers through r3's links. The pulse-edge system is alive only while the speculation is open; r3 fires only at/after commit-promotion. A computed read under `S` (pulse edge + `S`-slot) has its `S`-slot dropped on close and re-derives normally through r3 after the promoted signal fires. No consumer is fired by both systems for the same change.

**3. Driving speculative invalidation — pull, not r3's heap.** `edgesToFire(node, writeScope)` returns which pulse edges a speculative write should fire. The consumers of a speculative write are only computeds read *within the same speculation/action body* — because effects are forbidden inside speculative scopes (Q3). Those are read on demand, so invalidation is **pull**: a speculative write marks the affected `S`-slots dirty (drops `cached`), and the next pulse read under `S` recomputes via the path in (1). K1's Position-C (synchronous in-recipe fires) is honored by marking dirty synchronously at write time, so a write-then-read-downstream inside the body recomputes fresh. No scheduler and no use of r3's heap for the speculative case — r3's heap is only touched at commit (4). This is the cleanest fit and leans on r3 for nothing speculative.

**4. Commit batching — r3's heap already gives Q10.** r3's `setSignal` (index.ts:355) fires synchronously by inserting subs into the height heap, guarded by the `InHeap` flag (index.ts:60) so a shared downstream consumer is inserted **once** regardless of how many upstream signals changed; `stabilize()` (index.ts:394) drains low-height-first, recomputing each once, glitch-free. So Q10's "consumers see one invalidation per affected slot regardless of how many writes contributed" **falls out of r3's heap for free**, provided commit does *all* the `setSignal`s and *then* a single `stabilize()` (not a flush per write). pulse does not need its own deferred-fires region for the committed promotion — it needs to batch the promotion's writes before stabilizing. (Note: `src/signal.ts`'s setter currently calls `requestFlush()` per write; the commit path must instead promote-all-then-flush-once.)

**5. Firewall signals / `child` — orthogonal to scopes.** `signal(v, firewall)` (index.ts:131) creates a signal owned by a computed and links it into `computed.child`; `markNode` (index.ts:371) walks a computed's children to propagate `Check`. This is r3's mechanism for *computed-owned internal signals* (pulse's async computed uses it in `makeStageNode` for the published-value signal). It is not a transition/scope grouping mechanism and does not interact with the speculation scope layer. Ignore it for the scope overlay; it matters only to Plan 3's async-computed wiring, not to scopes.

**6. `height` — r3's concern for committed only; the overlay is height-agnostic.** r3 orders recompute by `height` for glitch-freedom (index.ts:395). The overlay's speculative recompute is pull-driven on read (1), ordered by read demand within the body, and never enters the heap — so it is height-agnostic. Height applies only to committed consumers fired by commit-promotion, which is entirely r3's existing machinery. No new height bookkeeping for speculation.

## What the findings imply

Every answer points the same way: **keep r3 untouched, run speculation as a pure overlay, and bridge to r3 only at commit.** Speculative state = `scope.slots` + pulse edges + chain-match + pull recompute; committed state = r3 as-is; commit = `closeScopeEdges` then batched `setSignal` + one `stabilize`. r3's heap supplies glitch-free, deduped committed propagation (Q10) for free; the overlay never needs r3's heap, height, or `Link`s for the speculative case. This is the "lean on r3 / minimal-delta" path and it requires no fork. Decision recorded in [ADR 0010](../adr/0010-speculation-overlay-above-r3.md).
